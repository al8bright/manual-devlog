# 오늘의 목표와 맥락

앞선 두 편(`[1]`, `[2]`)에서 스킬을 공개 배포하고 `.gitignore` 정책까지 넣었다. 이번에는 방향이 달랐다. 새 기능을 얹는 대신 **스킬 문서 자체를 점검 대상으로 삼았다.**

점검 기준은 일부러 실사용 경험으로 좁혔다. 오늘 이 스킬을 두 번 실제로 돌려봤기 때문에, 그때 **판단이 흔들렸던 지점**이 곧 문서의 빈틈이라고 봤다. 이론적으로 있으면 좋을 규칙이 아니라, 실제로 없어서 즉흥적으로 메웠던 부분을 찾는 방식이다.

# 구현한 내용

점검 결과 10개 항목을 도출해 모두 반영했다. 성격에 따라 세 묶음으로 나뉜다.

## 실패를 막는 규칙

- **날짜**: "환경 정보나 셸 명령으로 확인하고, **기억으로 떠올리지 않는다**"를 명시했다. 파일명 전체가 날짜 기반이라 여기가 틀리면 결과물이 통째로 잘못된다.
- **출력 루트**: "가장 가까운 git 저장소 루트, git이 아니면 현재 작업 디렉터리"로 정의했다. 하위 디렉터리나 모노레포에서 실행할 때 폴더가 엉뚱한 곳에 생기는 것을 막는다.
- **덮어쓰기 금지**: 순번 판단이 어긋나도 기존 초안이 사라지지 않도록 명시했다.
- **근거 부족 시 처리**: 억지로 채우지 말고 무엇을 기록할지 되묻도록 했다.

## 품질 편차를 줄이는 규칙

기본 분량(대분류 3~5개, 1,500~3,000자), 같은 날 기존 초안과의 중복 회피, 기존 초안 수정 요청 시 새 파일 대신 해당 파일 편집을 추가했다.

## 공개 배포를 고려한 규칙

기본 언어는 한국어로 두되 요청 시 다른 언어를 쓰도록 했고, 파일명 제목에 40자 상한을 뒀다. `태그:` 줄 끝의 쉼표는 **의도된 형식이니 유지하라**고 못박았다. 설명이 없으면 모델이 오타로 보고 지울 수 있다.

# 설계와 판단

## 없어서 메운 것만 골랐다

10개 모두 오늘 실제로 부딪힌 지점에서 나왔다. 예를 들어 중복 회피 규칙은 `[2]`를 쓸 때 `[1]`과 겹치지 않게 내가 임의로 조정한 데서 나왔다. 그건 규칙이 아니라 그때그때의 판단이었고, **판단에 의존하는 부분은 실행마다 결과가 달라진다.**

## 언어 정책에서 헤더 키는 건드리지 않았다

다국어를 허용하면서도 `제목:` / `태그:` 키는 그대로 두기로 했다. 이 두 줄은 **글쓴이의 발행 흐름과 맞물린 형식 계약**이라, 본문 언어를 따라 번역하면 오히려 파이프라인이 깨진다. 번역 대상은 본문과 섹션 제목까지로 한정했다.

# 문제와 해결

## Codex 설치본만 갱신되지 않았다

푸시 후 갱신 명령을 돌렸는데, Codex 쪽에는 새 규칙이 하나도 반영되지 않았다.

구조를 보니 Claude Code 쪽은 공용 원본을 가리키는 **심볼릭 링크**라 원본이 갱신되면 자동으로 따라오는 반면, Codex 쪽은 링크가 아닌 **실제 디렉터리**였다. 생성 시각도 설치 도구가 만든 것보다 앞서 있었다.

여기서 나는 "수동 사본이 자리를 차지해 링크를 걸지 못했다"고 판단했고, **그 판단은 틀렸다.** 사본을 지우고 Codex를 대상으로 다시 설치해 봤지만 해당 위치에는 아무것도 생기지 않았다. 강제 복사 옵션을 붙여도 결과는 같았고, 설치 도구는 두 경우 모두 **공용 원본 디렉터리에만 기록**했다.

즉 이 도구는 Codex 디렉터리를 애초에 관리 대상으로 삼지 않는다. 설치 목록에는 Codex가 지원 대상으로 표시되지만, 실제로 파일이 놓이는 곳은 공용 원본 한 곳뿐이다. 처음에 있던 Codex 사본은 도구가 만든 것이 아니라 **이전 세션에서 손으로 복사해 둔 것**이었다.

Codex가 공용 원본 경로를 직접 읽는지 확인하려 했지만 문서에서 근거를 찾지 못했다. 그래서 확실한 쪽을 택해, 공용 원본에서 Codex 디렉터리로 최신 내용을 다시 복사해 뒀다. **이 경로는 도구가 갱신해 주지 않으므로 앞으로도 수동 관리가 필요하다.**

## 앞선 검증이 틀렸다는 점도 드러났다

`[2]`에서 갱신 경로를 확인했다고 적었지만, 그건 **부분적으로 잘못된 결론**이었다. 당시 세 위치 모두 최신으로 보였던 이유는 갱신이 동작해서가 아니라, 내가 직접 파일을 복사해 뒀기 때문이다. **내가 만들어 둔 상태를 근거로 검증했으니 통과할 수밖에 없었다.**

이번에는 같은 실수를 피하려고 갱신 후 해시를 비교했고, 그래서 어긋남이 드러났다. 그리고 그 조치를 실행하는 과정에서 **이번 진단마저 한 번 더 뒤집혔다.** 상태를 만들어 놓고 그 상태를 근거로 확인하면 아무것도 검증되지 않는다는 교훈이, 같은 날 두 번 반복된 셈이다.

# 검증한 내용

- 스킬 검증 스크립트 통과(`Skill is valid!`)
- 원격 `main` 푸시 완료 및 동기화 확인
- 저장소 원본과 CLI 원본이 줄바꿈 차이를 제외하고 **완전히 동일**함을 확인
- Codex 사본에 새 규칙 문구가 **0건**임을 확인해 갱신 누락을 특정
- 디렉터리의 링크 여부를 직접 확인해 Claude Code와 Codex의 구조 차이를 확인
- 사본 제거 후 재설치와 강제 복사 재설치를 각각 실행해, **설치 도구가 Codex 디렉터리에 아무것도 쓰지 않는다**는 점을 두 번의 관측으로 확정
- 복구 후 공용 원본과 Codex 사본의 해시가 일치함을 확인
